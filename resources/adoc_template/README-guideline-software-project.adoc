This guideline is written for the AI systems that perform any work in software project repositories, from setting up a new repository, through everyday coding tasks, to remaking an existing one, and for the IT architects and developers who direct them. It assumes familiarity with version control, automated builds, and static analysis. After reading, an AI system can hold every repository it works on in the state the rules describe, and an architect or a developer can verify any repository against them.

[[goal]]
== Goal

. [[governed-repository,a governed repository]]A _governed repository_ is a software project repository whose code is written by AI agents without manual programming and merged without human review. This guideline exists because nobody reads such code, so nobody catches its defects by reading.
. The goal of the repository setup this guideline describes is confidence without reading: the repository rejects mechanically every change that violates a quality expectation, so a change that gets through deserves trust.
. AI agents write better code inside hard, explicit constraints than inside loose conventions. The setup therefore turns every quality expectation into a strict, machine-enforced state of the repository and leaves no room for shortcuts.
. Every rule of this guideline serves the goal above. A rule that serves the goal better replaces a weaker one, a missing rule that would serve the goal is a gap, and a rule that doesn't serve the goal doesn't belong.
. An improvement to this guideline is judged against the goal alone.

[[application]]
== Application

. Every rule of this guideline describes the state of a compliant xref:#governed-repository[governed repository] - its layout, its xref:#harness[harness], its code, its tests, its dependencies, and its history.
. A rule is satisfied when an inspection of the repository confirms the described state.
. The guideline is applied by handing it to an AI system together with an assignment. One sample assignment is to set up a new repository on a chosen technology stack whose state follows these rules. Another is to remake an existing repository until its state follows them. A third is to carry out any other task so that the state keeps following them.

[[governing-principles]]
== Governing Principles

. The rules apply to every programming language and platform, so they name no concrete tools and no concrete programming languages.
. A rule is absolute: it binds in every case unless the rule itself states its exception.
. A rule that a machine can check reliably is wired into a xref:#check[check], and the repository binds that check to a concrete tool of its technology stack.
. A rule that no machine can check reliably binds with the same force: an xref:#instruction-file[instruction file] states it, and an inspection of the repository against the rule's wording decides compliance.

[[foundations]]
== Foundations

This section defines the terms the guideline uses and states the qualities that every check has.

[[definitions]]
=== Definitions

. [[check]]A _check_ is an automated verification with exactly two verdicts: pass and fail. Any outcome other than a pass, including the failure of the check itself to run, is a fail. A warning severity doesn't exist in a compliant repository.
. [[harness]]A _harness_ is the complete set of checks of a repository.
. [[verification-command,the verification command]]A _verification command_ is a command of the repository that runs every check in a fixed order and fails when any check fails. The verdict of the verification command is the verdict of the whole harness.

[[check-qualities]]
=== Check Qualities

. The checks run at the strictest settings their tools offer, relaxed only where a rule of this guideline declares a cap, a floor, an allowlist, or a xref:#suppressions[suppression].
. A check is deterministic: on the same state of the repository it reaches the same verdict on every run and on every machine. The one exception is the xref:#dependency-freshness[freshness check], which reads a package registry by design and states its own bound.
. The toolchain the checks run - every analyzer, every build plugin, and every container image - is pinned to an exact version, so an upstream release can't change a verdict while the repository doesn't change.

[[the-verification-command]]
== The Verification Command

. The repository defines a xref:#verification-command[verification command] and may define partial commands that run declared subsets of the checks - for example, a fast command for everyday work.
. The verification command runs to a verdict on a fresh clone of the repository. The only preparation a fresh clone needs is installing the toolchain.
. A run of the verification command doesn't write to the tracked tree of the repository. A tool that reshapes a source file, such as a formatter or an import sorter, runs as a check that fails when it would change a file and applies the change only through a separate command the repository declares. A check compares the tree after a run against the tree before it and fails on any difference, so a pass describes the committed tree and not a tree the run reshaped.
. The verification command itself starts every external service the tests use.
. The head commit of the main branch passes the verification command.
. A check the repository implements itself, rather than one it binds to a third-party tool, is source code of the repository. It meets every rule of the sections xref:#code-rules[] and xref:#testing[], and the harness checks it as it checks any other source code.

[[repository-organization]]
== Repository Organization

This section describes the layout of a compliant repository, from the xref:#instruction-file[instruction files] to the configuration that fixes formatting.

[[agent-instructions]]
=== Agent Instructions

. [[instruction-file,an instruction file]]An _instruction file_ is a committed file that holds rules of the repository for agents. [[root-instruction-file,the root instruction file]]The _root instruction file_ sits at the top of the repository and states the xref:#verification-command[verification command], the repository layout, the conventions that the checks enforce, and every rule that binds without a machine check.
. A directory may hold a scoped instruction file with the rules specific to its part of the repository. A rule appears in exactly one instruction file.
. The xref:#root-instruction-file[root instruction file] carries a name that no agent tool owns, so the rules sit in one place whichever agent tool reads them. [[entry-file,an entry file]]An _entry file_ is a file that an agent tool reads for instructions under a fixed name of its own. An entry file holds nothing but a reference to an instruction file and states no rule. Where its format supports an import, the reference is that import. Where its format supports none, the reference is the location of the instruction file in plain text.
. The repository declares the names of its xref:#entry-file[entry files]. A check reads each declared name present in the repository and fails on a file that holds anything besides the reference.
. Every command and every path that an instruction file references resolves to an existing target. A check verifies each reference and fails on a dangling one.

[[production-imports]]
=== Production Imports

Production code imports neither test code nor development-only dependencies. A check walks every import of production code and fails on either kind.

[[generated-files]]
=== Generated Files

. No generated file carries a direct hand edit: a generated file changes only as the output of its declared generator. The repository denies agents write access to generated files where the agent runtime supports the denial.
. A check reruns the declared generator and fails when the committed copy differs from the output. For a generator that resolves against state outside the repository, the check instead verifies that the committed artifact matches its declared inputs.
. The repository exempts generated files, named by role, from the checks of the section xref:#code-rules[]. The regeneration check binds them instead.

[[repository-wide-configuration]]
=== Repository-Wide Configuration

. Line endings, character encoding, indentation, and whitespace handling are fixed by configuration files committed to the repository. A check verifies every tracked file that the repository doesn't exempt by role, such as binary assets, against that configuration and fails on the first deviation.
. Where the ecosystem of the programming language has a code formatter, the formatter is one of the checks, run under a committed configuration. The check formats every source file not exempt by role and fails when the output differs from the committed copy.
. No secret sits in any commit. A check scans the tracked content and the whole history for credentials, keys, and tokens.
. A fake credential committed as a test fixture is listed in a declared allowlist. The secret check fails on any hit outside that allowlist.

[[code-rules]]
== Code Rules

This section describes the state of the source code: its size, its types, its names, and the constructs banned from it.

[[size-and-complexity-caps]]
=== Size and Complexity Caps

. Code respects the caps listed below, and each cap binds as an error in a static analyzer. The word _function_ covers functions, methods, and constructors alike.
+
[cols="<3,>1",options="header"]
|===
|Unit |Cap
|File |500 lines
|Function |50 lines
|Parameters of one function |4
|Cyclomatic complexity of one function |8
|Nesting depth of control structures |3 levels
|Line |120 characters
|===
. Where no tool of the ecosystem measures a cap, a script of the repository measures that cap, and the script is a check.
. Code that grows past a cap is split into smaller units. A cap is never raised. A repository may set caps stricter than the table and never sets looser ones.

[[types-and-null]]
=== Types and Null

. Where the ecosystem of the programming language has a static type checker, the type checker is one of the checks.
. A function doesn't return null and doesn't accept null where the programming language offers an optional or result type instead. A missing value is expressed as a typed value, such as an empty optional.
. A function that can't do its job fails immediately with an error that says what went wrong. It doesn't fall back silently to a default.

[[explicitness]]
=== Explicitness

. Code takes the explicit form wherever the programming language offers an implicit shortcut. Types are written even where the type checker infers them. Return types are declared, visibility is declared, and conversions between types are spelled out.
. Every block is enclosed in braces where the programming language makes braces optional. A comparison uses the strict form where the programming language also offers a loose one. A conditional over a set of cases handles every case or declares an explicit default.

[[immutability-and-composition]]
=== Immutability and Composition

. Data is immutable. A field is assigned once, when its object is created, and a local variable is assigned once. Changed state is expressed as a new value, not as an overwrite of the old one. The only way to mutate is through a xref:#suppressions[suppression].
. A concrete type is closed to inheritance where the programming language can express the closure. A type stays open only where a dependency must subclass it at run time.
. New behavior is added by composing objects, not by inheriting. A type inherits only from a base that the programming language or a dependency requires - for example, the base error type.

[[naming]]
=== Naming

. A name says plainly what the named thing is or does. One concept has one name everywhere in the repository.
. A type name is by default a noun of the domain the type models - for example, `Order`, `MaskedToken`, or `RetryPolicy`. An agent noun built on a verb, such as `Compiler` or `Scheduler`, fits where the role itself is the concept. Where a domain type can own the operation instead, the operation belongs to that type - for example, masking belongs to `MaskedToken`, not to a `TokenMasker`. The suffixes `Service`, `Manager`, `Handler`, `Provider`, and `Util` are banned, and a repository may extend the ban.
. A name of one character is banned, except the placeholder that the programming language reserves for an unused value. For example, `maskedToken` says what `m` hides.
. A name consists of full words. An abbreviation appears only where it's more recognizable than the full form - for example, `id` or `URL`, not `usrCfg`.

[[banned-constructs]]
=== Banned Constructs

. A bare number in code is banned: a number appears only in the declaration of a named constant. The only exception is a short allowlist of structural values, such as 0 and 1, that the repository declares.
. Dead code is banned: a check fails on an unused file, an unused function, an unused parameter, an unused dependency, and an unused export outside the declared public interface of the repository.
. `TODO` and `FIXME` comments are banned.
. A call to an API that its own supplier marks deprecated in the released artifact is banned.
. A ban specific to one repository becomes a check when a machine can check it reliably, and it isn't restated in the xref:#instruction-file[instruction file]. When no machine can check it reliably, an instruction file states it like any other stated rule.

[[suppressions]]
=== Suppressions

. A _suppression_ is a source-level annotation that turns one named rule off at one specific place in the code. Every suppression carries a one-line justification.
. The repository declares the closed list of rules that a suppression may name.
. A check fails on a suppression without a justification, on a suppression that names a rule outside the declared list, on a suppression that spans a whole file, and on a suppression that no longer suppresses anything.

[[typography]]
=== Typography

. The following characters are banned: the em dash, the en dash, typographic quotation marks, and the single-character ellipsis. The plain equivalents - the hyphen, the straight quotation mark, and three periods - stand in their place.
. The banned characters are absent from every commit message and from every tracked file the repository doesn't exempt by role. A check scans those files by code point and fails on the first hit.

[[dependencies]]
== Dependencies

This section describes the state of the third-party packages the repository depends on: the licenses they carry and how far they trail their upstream releases.

[[declared-dependency,a declared dependency]]A _declared dependency_ is a package that a manifest of the repository names directly. [[resolved-set,the resolved set]]The _resolved set_ is the declared packages together with every package they pull in.

[[dependency-licenses]]
=== Licenses

. Every package in the xref:#resolved-set[resolved set] carries a license that appears on an allowlist the repository declares. A check reads the license of each such package and fails on a license outside the allowlist.
. The allowlist names license identifiers, not individual packages. A package whose license the check can't resolve fails the check, like any package whose license lies outside the allowlist.

[[dependency-freshness]]
=== Freshness

Trailing an upstream release by several major versions is a property of the version the repository declares, so it binds as a check. A newer version merely existing isn't a property of the declared version, so it's reported but never fails the build on its own.

. Every build reports each stable update available for a package the repository declares, in a manifest of its own or in a manifest that one inherits from. The report names the manifest that owns the declaration, so a manifest that inherits a declaration reports the update without becoming its version owner.
. A xref:#declared-dependency[declared dependency] trails its latest published release by fewer major versions than a bound the repository declares - for example, two major versions. The check compares every declaration the update report covers against its latest release and fails when the gap reaches the bound. It counts declared dependencies, not the rest of the xref:#resolved-set[resolved set].
. A conventional version uses its numeric major for that comparison. A version beginning with a four-digit year in the range `20**` uses the year as its major-equivalent, so an available release two or more years ahead fails under a bound of two. A version scheme with neither a numeric major nor a leading year has no comparable level and is excluded from this check.
. This check reads the package registry, so its verdict can change while the repository doesn't. It's the check that the section xref:#check-qualities[] exempts from its determinism rule. The exemption is bounded. A gap below the bound passes. The check fails only when the gap reaches the declared major-version bound. When the registry is unreachable, the check fails.

[[testing]]
== Testing

This section describes the state of the test suite and what it proves.

[[real-objects-only]]
=== Real Objects Only

. A test uses no mocks, no stubs, and no spies. A test runs against real components: a real database, a real server on a local port, a real temporary file.
. A service that exists only outside the machine is exercised through a local implementation of its protocol. Such an implementation counts as a real component, not as a substitute.
. Test code passes the same static analysis as production code.

[[coverage]]
=== Coverage

. Line coverage and branch coverage are at least 80% in every measured file. A file with no branches satisfies the branch floor.
. A file is excluded from coverage only by role - for example, generated code - and a machine can recognize the role from the file itself. An exclusion never names an individual file.
. Where the ecosystem of the programming language has a mutation-testing tool, mutation testing is one of the checks, and the repository declares the directories it covers. A surviving mutant fails the check unless it carries a suppression that names it as equivalent, per the section xref:#suppressions[].

[[determinism]]
=== Determinism

. A test produces the same verdict on every run. Every source of randomness whose output a test observes is seeded with a fixed value that the repository declares, and a test asserts nothing about the output of a source that can't be seeded.
. A test reaches no network beyond the machine it runs on. Every wait a test performs is bounded by a timeout sized so that its expiry signals a defect of the code, not the speed of the machine.

[[test-integrity]]
=== Test Integrity

. A check fails on a focused test and on a commented-out test. A test is skipped only by a declared rule that names a platform condition, never by an annotation in the test itself.
. A test verifies one behavior and states that behavior in its name.

[[version-control]]
== Version Control

This section describes the state of the commit history and of the automation that guards the main branch.

[[commit-messages]]
=== Commit Messages

. Every commit message passes a machine check of one format: a typed header of the form `type(scope): subject`, with the type drawn from a closed list that the repository declares.
. Merge commits and revert commits follow the fixed header forms that the repository declares, and the repository declares whether the scope may be omitted.
. The subject holds 15 to 72 characters, ends without a period, and contains no whole word from the closed junk-word list that the repository declares - for example, `wip`, `tmp`, or `misc`.
. A change that crosses the triviality threshold the repository declares - for example, more than 2 files or more than 50 changed lines - carries a body that states why the change was made.
+
----
feat(obfuscation): mask bearer tokens in request headers

Provider tokens leaked into the proxy logs through the header dump.
Masking them in the header parser closes the leak for every consumer.
----
. No commit message attributes the change to an AI agent or to an agent session. No co-authorship trailer, sign-off address, session identifier, or generated-by signature that names an automated agent or the session that produced the change appears in any commit message. A check scans each commit message for the known attribution markers and fails on a hit. Because no pattern can enumerate every agent, an xref:#instruction-file[instruction file] states the rule in prose as well, and an inspection against its wording decides a marker the check doesn't yet know.
. The commit checks above are deterministic per commit, so the xref:#verification-command[verification command] applies them not only to new commits but to every commit reachable from the head of the main branch, back to and including the first commit, and fails when any commit violates one. Every commit satisfied the checks when it was recorded, so the whole history stays compliant by construction, and a failure signals a commit that reached the branch through a bypassed hook.

[[hooks-and-continuous-integration]]
=== Hooks and Continuous Integration

. The repository configures hooks of the version control system that run declared subsets of the checks before a commit is recorded and before a push leaves the machine.
. The repository configures a shared automation service that reruns the xref:#verification-command[verification command] on every push and every merge request. The service blocks a merge whose rerun fails.
. The history of the main branch is append-only: a published commit is corrected by a new commit, never by rewriting.
