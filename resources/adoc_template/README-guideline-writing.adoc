This guideline governs how written documents are produced. Its purpose is to make documents precise, complete, easy to follow, and consistent across authors and over time.
ifdef::backend-html5+not-env-github[]
++++
<!-- vale English.Patronizing = YES -->
++++
endif::[]

The guideline applies to [[utilitarian-non-fiction,utilitarian non-fiction]]_utilitarian non-fiction_ - prose written to transfer accurate information from author to reader. Utilitarian non-fiction includes reference documentation, design documents, runbooks, README files, protocol descriptions, specifications, prose memos, and style guides, this guideline among them. The guideline doesn't apply to fiction, essays, memoirs, marketing copy, or transient chat.

The guideline is written for authors of such prose, whether human or AI. It assumes the ability to write standard English and familiarity with the subject the author writes about. After reading, an author should be able to apply each rule while writing and to verify a finished document against the rules.

The guideline is organized in four parts. xref:#part-1[Part 1] states rules that apply to any utilitarian non-fiction document. xref:#part-2[Part 2] adds rules for technical texts - documents whose subject is a technical system. xref:#part-3[Part 3] adds rules that apply when the author is an AI system. xref:#part-4[Part 4] adds rules for the AsciiDoc markup that carries the document.

[[part-1]]
== General Rules

This part states rules that apply to any xref:#utilitarian-non-fiction[utilitarian non-fiction] document, whatever its subject and markup. The parts that follow add rules for narrower contexts without overriding the rules stated here.

=== Audience, Purpose, and Scope

[#identify-audience]
==== Identify the Audience

A document names its primary reader at the beginning - the role, the assumed knowledge, and the decision the reader will make after reading. Rules that follow on style, depth, and vocabulary are calibrated to that reader. A document that doesn't identify its reader is calibrated to no one.

When the prompt or request names the reader, restate the reader's role and assumed knowledge in one sentence at the document's opening. This is calibration, not echoing - the document still owns its own framing. See xref:#dont-echo[].

[.bad-example]
.{bad-icon} Bad example
====
The Connection Pool Reference describes the connection pool.
====

[.good-example]
.{good-icon} Good example
====
The Connection Pool Reference is written for application engineers integrating against the database driver. It assumes familiarity with relational databases and connection lifecycle. It documents pool configuration, observable behavior, and tuning - enough to size and operate a pool against the supported drivers.
====

==== State the Purpose

A document states what it's for - the change in the reader's knowledge, capability, or behavior that the document is intended to produce. The purpose is named concretely enough that the reader can predict the kind of content that follows and judge, after reading, whether the document delivered.

[.bad-example]
.{bad-icon} Bad example
====
This document covers the rate limiter.
====

[.good-example]
.{good-icon} Good example
====
This document describes how the rate limiter behaves in production today and states the integration requirements that callers must satisfy. After reading it, an integrator should be able to send conforming requests, interpret the responses, and configure a quota for a new tenant.
====

==== Scope and Non-Scope

A document, and each major section, opens with a statement of what it covers. The scope statement bounds the topic precisely enough that the reader knows, before reading further, whether the document answers the question at hand. A non-scope statement is added only when a reasonable reader would otherwise expect the missing material to appear. A non-scope statement about material no one would expect is filler.

[.bad-example]
.{bad-icon} Bad example
====
(Document titled "The Order Service Reference" opens directly with: "An order is a record of a customer's intent to purchase one or more items...".) (No scope statement. The reader doesn't know whether the document covers the wire protocol, the storage format, the administrative interface, or all three.)
====

[.bad-example]
.{bad-icon} Bad example
====
(Document titled "The Order Service Wire Protocol" opens with: "This document covers the wire protocol of the Order Service. It doesn't cover unrelated subjects such as employee onboarding or office facilities.") (Scope is fine. The non-scope sentence addresses material no reader would have expected.)
====

[.good-example]
.{good-icon} Good example
====
(Document titled "The Order Service Reference" opens with: "This document specifies the wire protocol between client and server, the request and response formats, and the error model. The on-disk storage format and the replication protocol between server nodes are covered separately in the Storage Reference and the Replication Reference.") (Scope is stated. The non-scope is included because a reader of an "Order Service Reference" might reasonably expect storage and replication to be covered.)
====

=== Thought Structure

[#one-sentence-one-thought]
==== One Sentence, One Thought

A sentence carries exactly one assertion. If a sentence contains two independent claims joined by _and_, _but_, _while_, or a semicolon, split it. Compound sentences that link a cause to its consequence are acceptable when the link is the point. Sentences that staple two unrelated facts together aren't.

[.bad-example]
.{bad-icon} Bad example
====
The connection is established when the handshake completes, and a request is sent as a sequence of frames that are reassembled by the receiver in the order their stream identifiers appear.
====

[.good-example]
.{good-icon} Good example
====
The connection is established when the handshake completes. A request is sent as a sequence of frames. The receiver reassembles the frames in the order their stream identifiers appear.
====

[#one-paragraph-one-topic]
==== One Paragraph, One Topic

A paragraph develops one thought: a claim followed by its elaboration, qualifications, and consequences. When the topic shifts, the paragraph ends. A paragraph that introduces a second, parallel topic must be split, even when the two topics are related. The procedure in xref:#verify-every-paragraph[] verifies this structure before delivery.

[.bad-example]
.{bad-icon} Bad example
====
A transaction groups a series of operations into a single atomic unit and is started by calling `begin`. Indexes accelerate query execution by storing precomputed lookup structures and are maintained automatically by the database.
====

[.good-example]
.{good-icon} Good example
====
A transaction groups a series of operations into a single atomic unit. The transaction is started by calling `begin` and is concluded by either `commit` or `rollback`. Until the transaction is concluded, its changes are visible only to operations performed within the same transaction.

An index is a precomputed lookup structure that accelerates query execution. The database maintains an index automatically: every insert, update, and delete on the indexed table updates the index in the same transaction as the data change.
====

[#verify-every-paragraph]
==== Verify Every Paragraph

. Verification of the xref:#one-paragraph-one-topic[one-paragraph-one-topic rule] runs after the text is written, after every material reorganization, and before delivery. It covers every prose paragraph, every paragraph inside a list item, every continuation paragraph, and every table cell that contains more than one sentence. A repaired paragraph re-enters verification. The pass ends only when every paragraph receives the xref:#cohesive-verdict[cohesive verdict] defined below.
. Dissect one paragraph at a time before judging its prose. For every sentence, write its logical essence as a short subject-and-predicate statement. Remove transitions, emphasis, examples, and stylistic phrasing from the essence. This reduction exposes the topics that polished prose can conceal.
. State the paragraph's governing topic in one concrete sentence. Then assign every sentence one role under that topic: claim, elaboration, evidence, example, qualification, mechanism, or consequence. A sentence that requires a second governing topic doesn't belong in the paragraph.
. Test every boundary between adjacent sentences. Insert a hypothetical paragraph break at that boundary and read both resulting paragraphs.
.. If the break loses no meaning, logical dependency, contrast, emphasis, or causal force, presume that the sentences carry different topics and split them.
.. If the sentences carry one topic but remain equally clear after the break, rewrite them so their relationship is explicit. Make the later sentence visibly explain, evidence, qualify, implement, or follow from the earlier sentence. Naming the shared subject or the precise relationship is preferable to adding an empty transition such as _also_, _moreover_, or _in addition_.
.. If the break damages a necessary relationship that the wording already makes clear, keep the sentences together.
. Read the paragraph in xref:#forward-order[forward order]. The governing claim comes before its evidence or consequence, a cause comes before its effect, and a prerequisite comes before what depends on it. Reorder sentences when their logical essences reveal a stronger sequence.
. Assign one verdict and act on it at once:
.. [[cohesive-verdict,the cohesive verdict]]_Cohesive_ - one governing topic accounts for every sentence, every later sentence has an explicit role under it, and every pair passes the boundary test. No action follows.
.. _Rewrite_ - the sentences share one topic, but their relationship depends only on proximity or an ambiguous reference. Rewrite the paragraph until the relationship is explicit, then verify it again.
.. _Split_ - the paragraph contains parallel claims, independent mechanisms, separate boundaries, or any other second topic. Split at the topic change. Each resulting paragraph receives its own governing topic and re-enters verification.
. After a split, apply xref:#references-across-paragraphs[] and xref:#internal-references-with-xref[] to the new boundary. The first sentence of the new paragraph names and links any concept carried from the preceding paragraph. It never begins with shorthand whose meaning depends on the old paragraph.
. Finish with a whole-section read. Paragraphs must form a sequence in which the conclusion of one creates the premise or question answered by the next. This final read catches a paragraph that's internally cohesive but belongs under another heading or in another position.

[.bad-example]
.{bad-icon} Bad example
====
The gateway gives clients one network address. The gateway checks credentials, enforces request limits, and selects the destination service.

The sentences can be separated without losing meaning. Their shared topic is plausible, but the wording doesn't show how the second sentence develops the first.
====

[.good-example]
.{good-icon} Good example
====
The gateway provides one network address by checking credentials, enforcing request limits, and selecting the destination service for every client request.

The mechanism now explains how the gateway provides one entry point. Splitting the thought would damage that relationship.
====

==== No Restatement

A thought appears in exactly one place in the document. Two consecutive sentences that say the same thing in different words are a defect. A paragraph that ends by summarizing itself is a defect. When you find yourself rephrasing, delete the weaker version.

[.bad-example]
.{bad-icon} Bad example
====
The cache is invalidated when the source changes. Whenever the underlying data is modified, the cached copy is no longer valid and is therefore removed.
====

[.good-example]
.{good-icon} Good example
====
The cache entry for a record is invalidated when the record's `last++_++modified` timestamp changes.
====

==== Razor Sentences

ifdef::backend-html5+not-env-github[]
++++
<!-- vale English.We = NO -->
++++
endif::[]
Every sentence does work that no other sentence in the document does. If a sentence can be deleted without losing information, delete it. The usual offenders are sentences that announce upcoming material, sentences that summarize what was just said, and sentences that exist only to introduce a list. "In this section, we will discuss..." announces upcoming material. "There are several ways to do this:" introduces a list and can be deleted along with its colon.

[.bad-example]
.{bad-icon} Bad example
====
There are several important things to consider when configuring the load balancer. Let us look at them. The first thing is the algorithm. The algorithm controls how requests are distributed across backends.
====
ifdef::backend-html5+not-env-github[]
++++
<!-- vale English.We = YES -->
++++
endif::[]

[.good-example]
.{good-icon} Good example
====
The load balancer's algorithm controls how requests are distributed across backends. The supported algorithms are round-robin, least-connections, and consistent-hash. The default is round-robin.
====

[#forward-order]
==== Forward Order

Information flows from the general to the specific, from the prerequisite to the dependent, and from the cause to the consequence. The reader should never need a fact that the document hasn't yet introduced. When a concept is needed before its full definition, give a short gloss at first mention and link to the full definition.

[.bad-example]
.{bad-icon} Bad example
====
The `onMessage` callback is invoked after the channel has joined the topic. A channel is a logical connection identified by a name and bound to a single topic.
====

[.good-example]
.{good-icon} Good example
====
A channel is a logical connection identified by a name and bound to a single topic (see §3.2). When a channel joins a topic, it begins to receive messages published to that topic. Each message is delivered to the channel's `onMessage` callback.
====

==== Affirmative Before Negative

A claim states what something is or does before it states what it isn't or doesn't do. The affirmative gives the reader the fact to hold. The negation then refines the fact by ruling out an alternative the reader might otherwise assume. A negation placed first forces the reader to carry a list of exclusions with nothing yet to attach them to.

[.bad-example]
.{bad-icon} Bad example
====
Setting `cache.ttl` doesn't change the maximum number of entries or the eviction order. It controls only how long an entry remains valid after it's written.
====

[.good-example]
.{good-icon} Good example
====
Setting `cache.ttl` controls only how long an entry remains valid after it's written. It doesn't change the maximum number of entries or the eviction order.
====

==== Headings as Promises

A heading announces exactly what the section contains. The section delivers exactly that, no more and no less. A section titled "Authentication" describes authentication. It doesn't also describe authorization, even briefly. Material that doesn't belong under the heading goes into a separate section.

[.bad-example]
.{bad-icon} Bad example
====
Heading: "Connection Pooling." Body: discusses pooling, then transaction isolation, then a digression on prepared statements.
====

[.good-example]
.{good-icon} Good example
====
Heading: "Connection Pooling." Body: pool sizing, acquisition, release, leak detection, and the lifecycle of a pooled connection. Transaction isolation is documented in a separate section, with a cross-reference where pool behavior interacts with isolation.
====

[#declarative-headings]
==== Declarative Headings

A heading names its section's topic as a noun phrase or a declarative statement, such as "Connection Pooling" or "Off by Default." A heading isn't a question ("How Does Eviction Work?") and doesn't open with an interrogative lead-in ("How to Size the Pool"). A question in a heading withholds the information the heading exists to give, and it reads as a teaser in a table of contents. The material a question-style heading gestures at belongs in the body. The heading states the topic outright.

[.bad-example]
.{bad-icon} Bad example
====
The sections of a document on connection pooling are titled "Why Use Connection Pooling?" "How Does Eviction Work?" "How to Size the Pool," and "What Happens on Overflow."
====

[.good-example]
.{good-icon} Good example
====
The sections are titled "Connection Pooling Rationale," "Eviction Mechanics," "Pool Sizing," and "Overflow Behavior."
====

==== Self-Contained Prose

A heading is a navigational label, not part of the prose. The body reads correctly when every heading is removed: no sentence depends on its heading for a subject, a referent, or a qualifier. A reader who lands mid-section, or who reads the text with the headings stripped, loses no meaning. The body carries its meaning through its own content. It neither leans on the heading nor restates it.

[.bad-example]
.{bad-icon} Bad example
====
Heading: "Off by Default." Body: "Email and phone also ship off." With the heading removed, "off" has no referent: the reader can't tell what's off, or from what.
====

[.good-example]
.{good-icon} Good example
====
Heading: "Off by Default." Body: "Email and phone detection is off by default. To turn a rule on, set `enabled = true`." The state and the action stand without the title.
====

=== Terminology and Precision

[#strict-nomenclature]
==== Strict Nomenclature

. Give every concept one [[canonical-term,canonical term]]_canonical term_ and use that term throughout the document. The rule covers deliverables, actors, operations, states, boundaries, and units across prose, headings, lists, tables, diagrams, captions, and cross-reference labels.
. Keep two related terms only when they name different concepts. The concepts differ when they have different functions, owners, outputs, or lifecycles. If none of those properties differ, choose one term and replace the other.
. A comma-separated list, slash pair, or parenthetical alias is a violation when all terms name the same concept and the sentence gains no information from listing them.

[.bad-example]
.{bad-icon} Bad example
====
After authentication, the service creates a session. The login context stores the user identifier. The authentication state expires after 30 minutes.
====

[.good-example]
.{good-icon} Good example
====
After authentication, the service creates a session. The session stores the user identifier and expires after 30 minutes.
====

[.bad-example]
.{bad-icon} Bad example
====
Editors select a page, fill the template with content, and publish the layout.
====

[.good-example]
.{good-icon} Good example
====
Editors select a page template, add content, and publish the page.
====

[#verify-nomenclature]
==== Verify Nomenclature

. Verify compliance with the rule xref:#strict-nomenclature[] after drafting, after every material reorganization, and before delivery. A repaired term re-enters the check.
. Collect repeated noun phrases from prose, headings, lists, tables, diagrams, captions, and cross-reference labels.
. Group terms that appear to name the same concept. Choose one xref:#canonical-term[canonical term] for each group and replace its aliases.
. Check that each term names only one concept. If a term names more than one concept, split the term or narrow its definition and rename the outlying uses.
. Keep related terms only when they name different concepts and each term is used consistently. When several terms name the same concept, remove terms that add no information.
. Finish when each concept has one term and each term names one concept. A text search or linter may find candidates, but the final decision depends on the concepts named in context.

[#defined-terms]
==== Defined Terms

A term that has a specific meaning in the document is defined the first time it's used in a normative sense. The definition takes the form _X is Y that Z_. _Y_ is the genus - the broader category. _Z_ is the differentia - what distinguishes _X_ from other members of _Y_. After the definition, the term is used without redefinition.

[.bad-example]
.{bad-icon} Bad example
====
A token is something the client sends to prove who it is.
====

[.good-example]

====
A _token_ is an opaque string issued by the authentication server that the client presents to prove its identity to a resource server. A token has an issuer, a subject, an expiration time, and a set of scopes that constrain the operations the bearer may perform.
====

[#concrete-vocabulary]
==== Concrete Vocabulary

ifdef::backend-html5+not-env-github[]
++++
<!-- vale English.Marketing = NO -->
++++
endif::[]
Use words that two competent practitioners would interpret the same way. When two reasonable readers would disagree on what a word means in context, the word is too vague. Replace abstract qualifiers - _flexible_, _robust_, _scalable_, _modern_, _enterprise-grade_, _seamless_, _intelligent_, etc. - with the specific properties they hide.

[.bad-example]
.{bad-icon} Bad example
====
The platform is flexible and supports seamless integration with modern enterprise systems.
====
ifdef::backend-html5+not-env-github[]
++++
<!-- vale English.Marketing = YES -->
++++
endif::[]

[.good-example]
.{good-icon} Good example
====
A new data source is added by implementing the `DataSource` interface and registering it through the plugin manifest. The platform discovers the implementation at startup. Existing sources don't need to be modified or recompiled, and existing queries continue to run unchanged.
====

==== Plain Names for Plain Things

Prefer the older, well-understood term over a newer marketing-laden one when both denote the same thing. Use the fancier term only when it carries information the plain term lacks. The test is whether replacing the fancier term with the plain one would lose meaning. When it would not, the fancier term was decoration.

ifdef::backend-html5+not-env-github[]
++++
<!-- vale English.Formal = NO -->
++++
endif::[]
[.bad-example]
.{bad-icon} Bad example
====
The system leverages a cloud-native, distributed compute fabric to deliver intelligent responses.
====
ifdef::backend-html5+not-env-github[]
++++
<!-- vale English.Formal = YES -->
++++
endif::[]

[.good-example]
.{good-icon} Good example
====
Each request is processed by one of several stateless servers behind a load balancer. The server consults a cache, then the database, then returns the response.
====

Further pairs where the plain form is usually correct:

. _server_ over _compute node_,
. _file_ over _blob_ (when it's a file),
. _call_ over _invocation_ (when it's an ordinary function call),
. _list_ over _collection_ (when the order matters),
. _user_ over _actor_ (when it's a person).

==== Acronyms and Abbreviations

An acronym is expanded the first time it appears in the document and the first time it appears in each major section, in the form _Expanded Form (ACRONYM)_. After expansion, the acronym is used. Acronyms more recognizable than their expansions - HTTP, URL, JSON, XML, SQL, TCP - need not be expanded, except where the expansion adds information the reader needs.

.{bad-icon} Bad example

Replicas discover each other and detect failures using the Scalable Weakly Consistent Infection-style Membership (SWIM) protocol, which runs over Quick UDP Internet Connections (QUIC).
====

=== Context and Framing

==== Set the Stage

Before describing a topic in detail, locate it in the broader landscape. Name the category it belongs to, the problem it solves, and how it relates to adjacent concepts the reader is likely to know. The introduction need not be long. It must give the reader a place to put the new information.

[.bad-example]
.{bad-icon} Bad example
====
The query planner uses a cost-based optimizer with histograms.
====

[.good-example]
.{good-icon} Good example
====
A relational database receives queries in a declarative language (SQL) and must decide how to execute them. This is the job of the _query planner_: it transforms a SQL statement into an executable plan - a tree of operations such as scans, joins, and aggregations.

The planner described in this document is _cost-based_: it enumerates candidate plans and chooses the one with the lowest estimated cost. Cost is estimated using _histograms_ - summaries of column value distributions, refreshed periodically - which let the planner predict how many rows each operation will produce.
====

==== Outer Topics in Outline Only

When a topic touches an outer topic, summarize the outer topic in just enough detail for the current discussion. Don't reproduce its full documentation. Reference the authoritative source. The summary covers the slice of the outer topic that the current text depends on, no more.

[.bad-example]
.{bad-icon} Bad example
====
A section on rate limiting that opens with five paragraphs explaining what HTTP is, what status codes are, and how clients and servers communicate.
====

[.good-example]
.{good-icon} Good example
====
Rate limiting is the mechanism by which an HTTP server protects itself from excessive requests by a single client. When a client exceeds its quota, the server responds with status `429 Too Many Requests` and a `Retry-After` header indicating when the client may try again. The full semantics of HTTP status codes and headers are defined in the HTTP specification.
====

==== Purpose Before Mechanism

Before describing a mechanism, state what the mechanism is for. The reader needs the purpose to evaluate the mechanism. The purpose statement takes one or two sentences. It doesn't become a sales pitch.

[.bad-example]
.{bad-icon} Bad example
====
The deduplication subsystem maintains a Bloom filter of recent message IDs and consults it on each incoming message.
====

[.good-example]
.{good-icon} Good example
====
The same message can arrive more than once: producers retry on timeout, and the network can reorder and duplicate packets. To deliver each message to the application at most once, the receiver deduplicates incoming messages by ID. A Bloom filter of recent IDs serves as the first check. On a positive match, the receiver consults the durable index to confirm.
====

=== Concreteness and Examples

[#show-then-tell]
==== Show, Then Tell

Where a concept can be illustrated - by an example, a sample, a worked-out case, a quotation - show it. The illustration follows the definition. It doesn't replace it. Definitions establish meaning. Illustrations confirm it. When the concept has interesting boundaries - empty inputs, missing inputs, partial information, edge cases - illustrate at least one boundary alongside the typical case. Misreadings tend to arise at boundaries.

[.bad-example]
.{bad-icon} Bad example
====
A query parameter is appended to the URL after the path and is used to pass additional data to the server.
====

[.good-example]
.{good-icon} Good example
====
A query parameter is appended to the URL after the path, separated from the path by `?` and from other parameters by `&`. The following URL has two query parameters, `q` and `page`:

....
https://example.com/search?q=postgres+index&page=2
....

A parameter without a value is permitted. Its value is the empty string. A parameter that appears more than once produces a list of values whose order matches the order in the URL:

....
https://example.com/search?tag=db&tag=index&debug
....
====

[#realistic-examples]
==== Realistic Examples

Examples use names, values, and scenarios that resemble real usage: `OrderService`, `customer++_++id`, `/var/log/app.log`. Avoid `Foo`, `Bar`, `xxx`, and `myThing` except in the most abstract illustrations. Realistic examples carry information about typical usage. Placeholder examples don't.

[.bad-example]
.{bad-icon} Bad example
====
Acme Corp. agrees to provide widgets to Beta Ltd. on a date in the future.
====

[#mark-illustrative-cases]
==== Mark Illustrative Cases

An illustrative value, figure, or scenario is marked as illustrative. When a single number or case stands in for a range of possibilities the author hasn't enumerated, a phrase such as _for example_, _for instance_, _say_, or _one such case_ signals that it illustrates the rule rather than stating it. An unmarked illustration reads as a categorical rule, so the reader takes the one value as the fixed policy and acts on it. State the rule first, then mark the example that follows. This rule complements xref:#no-false-universals[]. A false universal overstates an uncertain claim, and an unmarked example overstates the reach of a single case.

[.bad-example]
.{bad-icon} Bad example
====
A tool that replaces a €5,000 consulting engagement is priced at €1,200 to €3,600 per year. (One illustrative mapping, phrased as the pricing rule. The reader takes €1,200 to €3,600 as the fixed price.)
====

[.good-example]
.{good-icon} Good example
====
The price is anchored to the value the tool delivers. For example, a tool that replaces a €5,000 consulting engagement might be priced at €1,200 to €3,600 per year.
====

=== Language and Style

==== Active Voice and Named Actor

A sentence names the actor that performs the action. Passive voice is reserved for cases where the actor is genuinely unknown, irrelevant, or the topic of the sentence. "The request is rejected" is acceptable when the topic is the request, not the rejecter.

[.bad-example]
.{bad-icon} Bad example
====
The configuration is loaded and the cache is populated. (Who loads it? Who populates the cache?)
====

[.good-example]
.{good-icon} Good example
====
On startup, the configuration loader reads `config.yaml` from the working directory and populates the in-memory cache.
====

==== Direct Verbs

Replace nominalizations with the underlying verbs. _Perform an analysis of_ becomes _analyze_. _Make a decision about_ becomes _decide_. _Provide support for_ becomes _support_. The shorter form is also more precise, because the verb carries the action that the nominalization had abstracted away.

[.bad-example]
.{bad-icon} Bad example
====
The framework performs the resolution of dependencies and provides notification of state changes.
====

[.good-example]
.{good-icon} Good example
====
The framework resolves dependencies and notifies registered listeners of state changes.
====

==== Avoid Parentheses and Semicolons

A parenthetical buries content the reader still has to process. When the content matters, write it as a separate sentence. When it doesn't matter, delete it. A semicolon joins two independent clauses into one sentence, which xref:#one-sentence-one-thought[] forbids - split the clauses into two sentences.

++++
<!-- vale English.Semicolons = NO -->
++++
endif::[]
[.bad-example]
.{bad-icon} Bad example

The connection pool (default size 10) is configured via `pool.size`; the value is read at startup.

++++
<!-- vale English.Semicolons = YES -->
++++
endif::[]

[.good-example]
.{good-icon} Good example

The connection pool is configured via `pool.size`. The default size is 10. The value is read at startup.
====

[#no-false-universals]
==== No False Universals

A claim in the form _X is Y_ or _X does Z_ asserts that the claim holds in every case. Write that form only when no case is excluded. When the behavior is a possibility, a permission, or one case among several, write the modality that holds: _can_, _may_, or the condition under which the claim is true. A query can use an index. The response is served from the cache on a hit and from the database on a miss.

[.good-example]

[#pronoun-antecedents]
==== Pronoun Antecedents

Every pronoun - _it_, _this_, _they_, _that_ - has a single, unambiguous antecedent in the same sentence or the immediately preceding sentence. When the candidate antecedents are two or more, replace the pronoun with the name. _This_ and _that_ at the start of a sentence are followed by the noun they refer to - _this change_, _that release_ - when the antecedent isn't a single noun.

[.bad-example]
.{bad-icon} Bad example
====

====

[.good-example]
.{good-icon} Good example
====
The handler calls the resolver. The resolver logs the request and returns the result to the handler.
====

[#references-across-paragraphs]
==== References Across Paragraphs

A concept introduced in an earlier paragraph enters a later paragraph by name. A demonstrative shorthand - _this split_, _that mechanism_, a bare _This_ - doesn't reach across the paragraph boundary: the new paragraph offers no antecedent, so the reader guesses among every candidate of the previous one. The first mention in the new paragraph is specific. It uses the xref:#defined-terms[defined term] where one exists, or a noun phrase that identifies the concept with no rival reading. Later mentions inside the same paragraph may then shorten to pronouns within the limits of xref:#pronoun-antecedents[].

[.bad-example]
.{bad-icon} Bad example
====
(A paragraph describes an eviction policy and a refresh schedule. The next paragraph opens with: "This mechanism also covers the session cache.") (Two candidate mechanisms precede. The demonstrative picks neither.)
====

[.good-example]
.{good-icon} Good example
====
(The next paragraph opens with: "The eviction policy also covers the session cache.") (The referent is named, so the reader resolves it without rereading the previous paragraph.)
====

[#inclusive-language]
==== Inclusive Language

Name actors and examples without invoking gender, ethnicity, or other identity attributes unless they're part of the topic. Use _they_ as a singular pronoun for a person of unspecified gender. Use names from a variety of traditions in examples, not from a single naming convention. Avoid metaphors that depend on culturally specific knowledge for a reader who may not share it. Replace terms whose origin demeans a group. The established replacements - _allowlist_ / _blocklist_, _primary_ / _replica_, _main_ branch, etc. - communicate at least as well.

[.bad-example]
.{bad-icon} Bad example
====
When the user clicks Submit, he is shown the receipt. If his card is declined, ask him to retry.
====

[.good-example]
.{good-icon} Good example
====
When the user clicks Submit, the receipt is shown. If the card is declined, the user is prompted to retry.
====

=== Document Mechanics

[#section-nesting]
==== Section Nesting

A section can have any number of subsections. A subsection can nest further subsections when the material requires it. Two limits bound this nesting.

First, subsections nest at most four levels below a top-level section, so a heading is at most five levels deep counting the top-level section. In xref:#part-4[AsciiDoc], a top-level section is written `==` and each deeper level adds one `=`, making `======` the deepest permitted heading:

[source,asciidoc]
----
== 1
=== 2
==== 3
===== 4
====== 5
----

Second, a section has zero subsections, or two or more. A lone subsection means either that its content belongs in the parent section's prose or that a sibling subsection is missing.

[.bad-example]
.{bad-icon} Bad example
====
[source,asciidoc]
----
== Configuration
=== Connection Pool
The connection pool is configured via `pool.size`.
----

(One section, one subsection.)
====

[.good-example]
.{good-icon} Good example
====
[source,asciidoc]
----
== Configuration
The connection pool is configured via `pool.size`.
----

(The lone subsection's content is folded into the parent section.)
====

[.good-example]
.{good-icon} Good example
====
[source,asciidoc]
----
== Configuration
=== Connection Pool
The connection pool is configured via `pool.size`.
=== Cache
The cache is configured via `cache.ttl`.
----

(Two sibling subsections.)
====

[#cross-references]
==== Cross-References

A cross-reference points to a numbered section, table, figure, or defined term. References to "above" and "below" are permitted only within the same paragraph or list. Across sections, use the section number. In AsciiDoc documents, the anchor that a cross-reference targets and the markup that carries the cross-reference are governed by the sections xref:#explicit-anchors[] and xref:#internal-references-with-xref[].

[.bad-example]
.{bad-icon} Bad example
====
As discussed earlier, the resolver follows specific rules.
====

[.good-example]
.{good-icon} Good example
====
The resolver follows the rules defined in §5.3.
====

[#lists-for-enumerable-content]
==== Lists for Enumerable Content

. An _enumeration list_ presents genuinely parallel, enumerable content: a fixed set of states, a finite set of options, or a sequence of steps. Prose presents arguments, derivations, and connected reasoning. Keep connected reasoning in prose, and present parallel enumerable content as separate list items. Every enumeration list is ordered, even when its order only gives the items stable addresses.

. Every enumeration list follows these rules:

.. A complete sentence immediately precedes the list and ends with a colon. A parent item that introduces a nested list serves as its lead-in and also ends with a colon. A colon can also introduce one literal example, such as a command or code block.
.. Every level contains at least two items. A lone item is prose, just as xref:#section-nesting[] forbids a lone subsection.
.. Every item at a given level uses one of two forms uniformly.
... _Sentence-form_ items begin with an uppercase letter and end with terminal punctuation. A question mark or exclamation mark can replace a period, and a colon is allowed only when the item introduces a nested list. Case-sensitive syntax can require a different initial letter.
... _Fragment-form_ items begin with a lowercase letter and end with a comma, except that the final item ends with a period to close the enumeration. A fragment that introduces a nested list ends with a colon instead. A proper noun, acronym, quoted label, or case-sensitive token keeps its required capitalization.

[.bad-example]
.{bad-icon} Bad example
====
The supported states are

* received,
* The request is authorized.
====

[.good-example]
.{good-icon} Good example
====
The system starts in four phases. First, it reads the configuration file. Second, it validates the configuration against the schema. Third, it resolves references between configuration sections. Fourth, it applies each resolved section in ascending order of priority.
====

Sentence form is appropriate when each item is a complete statement:

[.good-example]
.{good-icon} Good example
====
A request is in exactly one of the following states:

. Received means that the request has been parsed but not yet authorized.
. Authorized means that the caller has been authenticated and authorized.
. Processing means that the handler is executing.
. Completed means that the response has been sent.
. Failed means that the handler raised an unhandled error.
====

Fragment form is appropriate when the items complete the lead-in sentence:

[.good-example]
.{good-icon} Good example
====
The supported output formats are:

. `html`,
. `pdf`,
. `docx`.
====

[#exhaustive-lists]
==== Exhaustive Lists

A list is either complete or explicitly marked as incomplete. When the list enumerates the members of a set, all members appear. When the list is a sample, it opens or closes with a phrase that names the omission - _among others_, _the most common are..._, _see §X for the full list_. A list that looks complete but omits members is a defect: a reader who acts on the listed items as the full set acts on a false premise.

[.bad-example]
.{bad-icon} Bad example
====
The supported authentication methods are password, OAuth, and SAML. (The system also supports certificate-based authentication and an external IdP integration, but the list reads as exhaustive. A reader who designs an integration around the three listed methods discovers the gap only during implementation.)
====

[.good-example]
.{good-icon} Good example
====
The supported authentication methods are password, OAuth, SAML, certificate-based authentication, and external IdP integration.
====

[.good-example]
.{good-icon} Good example
====
The most commonly used authentication methods are password, OAuth, and SAML. The full set, including certificate-based and external-IdP methods, is listed in §6.2.
====

A table is used when each item has the same set of attributes and the reader will compare across attributes. A table isn't used as a layout device for text that isn't tabular. Each column has a header. Each row is independent.

|AUTHORIZED |no |yes |no
|PROCESSING |no |yes |no
|COMPLETED |yes |yes |no
|FAILED |yes |yes |yes
|===
====

[#sources-and-attribution]
=== Sources and Attribution

A [[source,source]]_source_ is a document consulted during writing: provided with the request, or found and read while researching it.

[#claim-classes]
==== Claim Classes

A statement that draws on xref:#source[sources] belongs to exactly one of three classes, and the class fixes its citation duty. A [[reported-claim,reported claim]]_reported claim_ is a statement that restates what a source says. An [[inferred-claim,inferred claim]]_inferred claim_ is a conclusion that the author derives from one or more sources. An [[author-supplied-claim,author-supplied claim]]_author-supplied claim_ is a statement the author makes on their own authority, without a source: own expertise or common knowledge.

A xref:#reported-claim[reported claim] cites every source it restates. An xref:#inferred-claim[inferred claim] cites every source it draws on and is marked as an inference. A claim that rests on three sources, for example, cites all three. An xref:#author-supplied-claim[author-supplied claim] carries no citation. The classes close the text in both directions: every statement derived from a source carries a citation, and every statement without a citation must stand as author-supplied. A document whose every statement is author-supplied - a style guide written from expertise, for example - carries no citations and no source list.

The xref:#request-source[request] that commissioned the text falls on both sides of the citation duty. A statement that reports what the request says is a xref:#reported-claim[reported claim] and cites the request. An instruction the author merely follows - a length cap, a topic to emphasize - shapes the text without being asserted in it, so there is nothing to cite. [[origin-test,the origin test]]The test is origin, not confidence: a particular that exists only because the request states it - a date, a volume, a constraint specific to the requester - is reported and cites the request. A statement that any competent author could make without the request is xref:#author-supplied-claim[author-supplied].

[.bad-example]
.{bad-icon} Bad example
====
The customer requires delivery by 2026-11-30 and an availability of 99.9%. Splitting the rollout into two phases would reduce the delivery risk. (The first sentence reports the customer's request for proposal and the second is an inference from it, but neither is cited, so the reader can't tell reported facts and derived conclusions from the author's own claims.)
====

[.good-example]
.{good-icon} Good example
====
The customer requires delivery by 2026-11-30 and an availability of 99.9%. Both facts cite the request for proposal. The recommendation to split the rollout into two phases cites the same document and is marked as an inference. The remark that a phased delivery is established practice carries no citation, because it rests on the author's expertise.
====

A xref:#reported-claim[reported claim] asserts no more than its quote states in the source's own words. A count, a total, an aggregate over several items, or a second fact composed into the same sentence is content the author synthesized, not content the source reported in that form. Such a statement is an xref:#inferred-claim[inferred claim] that cites the items it rests on, or an xref:#author-supplied-claim[author-supplied claim] - never a reported claim backed by a quote of one item, because the quote of one item can't support a claim about the whole set.

[.bad-example]
.{bad-icon} Bad example
====
The specification defines eight endpoints. (The citation quotes the definition of one endpoint. The quote names that endpoint and says nothing about how many exist, so it can't support the count of eight.)
====

[.good-example]
.{good-icon} Good example
====
The count is written as an inference: _eight endpoints_ carries the _Inferred from_ prefix and cites the endpoint list it rests on. When the source states the count in its own words, the claim reports it and quotes that sentence instead.
====

[#closed-source-list]
==== Closed Source List

A document that cites sources ends with a list of them - in AsciiDoc, the bibliography that a xref:#bibliography-markup[dedicated section] defines. The list is closed in both directions. Every citation in the text resolves to a listed source. Every listed source is cited at least once, so a source that no statement rests on is removed from the list. The xref:#request-source[request] that commissioned the text - the brief from the requester - is a citable source like any other.

[.bad-example]
.{bad-icon} Bad example
====
A footnote cites "the vendor's pricing sheet," but the document lists its sources nowhere, so the reader can't tell which file, which version, or which vendor. A closing "Further reading" section names three reports that no statement cites.
====

[.good-example]
.{good-icon} Good example
====
Every footnote points into the document's source list. The source list holds exactly the five sources the footnotes use: the request for proposal, the pricing workbook, a product screenshot, one web page, and the brief from the requester.
====

[#source-identity]
==== Source Identity

Every listed source is identified precisely enough that the reader can obtain the exact artifact the author used - not a similar one, not a later revision. The identity is stated in named fields of four groups. `Title` is common to every source and names it: the document's own title, the standard's name, a one-line description of an image. The three remaining groups are dimensions with one subsection each: the xref:#source-class[class] states how the reader can reach the source, the xref:#source-types[type] names the kind of artifact, and the xref:#source-status[status] states the artifact's standing.

....
                  +--------------+
                  | source entry |
                  +--------+-----+
                           |
      +-------------+------+------+-------------+
      |             |             |             |
      v             v             v             v
+-----------+ +-----------+ +-----------+ +-----------+
|   title   | |   class   | |   type    | |  status   |
| the name  | | how the   | | what kind | | what      |
| of the    | | reader    | | of        | | standing  |
| source    | | reaches it| | artifact  | | it has    |
+-----------+ +-----------+ +-----------+ +-----------+
....

An entry states its `Title`, every required field of its class and type, and the optional fields that apply, in the catalog order. The field names are exact. A required field whose value the author can't establish states the literal value _unknown_, so the reader sees a gap that was checked rather than skipped. An optional field whose value is unknown is omitted. A class field is never unknown, because it records the author's own acts: the archiving, the access, the request.

[.bad-example]
.{bad-icon} Bad example
====
The numbers come from the pricing spreadsheet the customer sent. (Which file, which version, sent when, stored where? The claim can't be re-checked against the artifact the author used.)
====

[.good-example]
.{good-icon} Good example
====
The entry's fields read: `Title` - 2026 Pricing Sheet. `Type` - Workbook. `Owner` - the customer's procurement office. `Date` - 2026-05-20. `Archived as` - the repository path. `SHA-256` - the digest of the archived bytes.
====

[#source-class]
===== Source Class

A _class_ states how the reader can reach a source, in one of four forms:

. An [[archived-file,archived file]]_archived file_ is any source that exists as a file or was captured as one. The class spans documents, workbooks, presentations, email files, images, and code, among others, wherever they came from. It also spans content with no file form of its own - a database extract, a retrieval from an external tool, a page behind a login - saved to a file when it was consulted. The file is copied under `.docs/sources/` beside the document. Its fields name the archive path (`Archived as`) and the digest of the archived bytes (`SHA-256`).
. A [[web-source,web source]]_web source_ is content that stays reachable at a URL. Its fields give the address (`URL`) and the access date (`Accessed`). A page that needs credentials or a subscription is still a web source, and the `Access` field then names the requirement.
. A [[request-source,request]]_request_ - the brief that commissioned the text - carries the fields `Request of` (its date) and `By` (the channel it arrived through). It stays outside the archive, carries no digest, and takes no type. Material pasted into or attached to the request - a screenshot of a conversation, an interface, code, or an error, a photograph of an object, a file - is saved and listed as an xref:#archived-file[archived file].
. A source that can't or must not be copied is declared with the field `Not archived`. Its value states the form of the canonical copy. Common forms are a paper book, a licensed standard, a confidential case file, and a live production system.

When the document is committed to version control, its xref:#archived-file[archived files] are committed with it. A committed file can't change without a trace, so the entry's digest keeps matching the file the author cited.

[#source-types]
===== Source Types

A [[source-type,type]]_type_ names what kind of artifact a source is and fixes the fields that describe it. The catalog below is closed, and a source that fits no listed type takes _Other_.

A field is required only when it's constitutional for its type - every artifact of the type has it, the way every email has a sender and every image depicts something. Every other field is optional and stated when known.

[cols="1,2,2",options="header"]
|===
|Type |Required fields |Optional fields
|Contract |`Parties` |`Concluded on`, `Governing law`
|Legal source |`Issuing body`, `Identifier` |`Date`
|Official record |`Register` |`Entry number`
|Financial record |`Issuer` |`Kind`, `Number`, `Date`, `Amount`
|Correspondence |`Participants` |`Platform`, `Sender`, `Addressee`, `Sent on`, `Time range`, `Subject`
|Email |`Sender`, `Sent on` |`Recipients`, `Subject`, `Time range`
|Minutes |`Held on` |`Participants`, `Recorder`
|Report | |`Author`, `Date`, `Period covered`
|Specification |`System` |`Author`, `Date`, `Version`
|Standard |`Identifier` |`Issuing body`, `Year`, `Version`
|Publication |`Authors` |`Year`, `Publisher`, `Edition`, `ISBN`, `DOI`
|Web page | |`Site`, `Published on`
|Presentation | |`Author`, `Date`, `Slides`
|Workbook | |`Owner`, `Date`, `Sheets`
|Ticket |`Tracker`, `Ticket number` |`Ticket state`
|Repository |`Host and path` |`Commit`, `Branch`
|System output |`System` |`Query`, `Captured on`
|Image |`Depicts` |`Captured as`, `Captured on`, `Place`
|Recording |`Medium` |`Date`, `Participants`, `Duration`
|Other |`Description` |`Date`, `Version`
|===

An `Email` entry names its `Sender` by address, and prefixes a display name when the source carries one. Its `Sent on` field records the date and the exact time the message was sent, so two messages of the same day stay distinguishable.

An _Other_ entry describes the source in `Description` and gives the best available date or version, so the fallback can't produce an identity-free entry.

The boundaries that recur resolve as follows:

. _Email_ or _Correspondence_ - delivered by email, or through any other channel,
. _Report_ or _Specification_ - describes findings, or prescribes a system,
. _Report_ or _Publication_ - internal or commissioned, or published in an edited venue,
. _Contract_ or _Correspondence_ - executed by the parties, or sent by one,
. _Image_ or _System output_ - pixels, or text: a screenshot of an error is an Image, the copied error text is System output,
. _Minutes_ or _Recording_ - the written record, or the media file of the same meeting,
. _System output_ or _Publication_ for a dataset - extracted by the author, or published with its own identifier.

[#source-status]
===== Source Status

A _status_ states the standing of the artifact in the `Status` field: `draft` for work in progress, or `final` for the released form - executed, published, sent, in force. Free elaboration follows the word - _draft v3 of 2026-07-15_, _final, executed 2026-07-30_. An entry of the xref:#source-types[Contract type] states its status always. Other entries state it whenever the standing is contestable.

Status bounds support. The standing is part of the context in the support test of xref:#quote-and-locator[], so a claim that asserts more standing than its source has takes xref:#unsupported-verdict[]. A draft supports claims about the draft. The final instrument supports claims about what was agreed, released, or enacted.

[.bad-example]
.{bad-icon} Bad example
====
A memo cites the `docx` draft of a services agreement for the claim that the parties agreed to a 30-day payment term. The draft proposed the term. Only the executed instrument knows whether the parties agreed to it.
====

[.good-example]
.{good-icon} Good example
====
The entry for the signed PDF carries `Status` - final, executed 2026-07-30. The memo cites it for the agreed term, and cites the draft entry only for the drafting history.
====

[#citation-scope]
==== Citation Scope

The unit of citation is the sentence. A citation marker at the end of a sentence covers exactly that sentence. A marker placed inside a sentence covers the text from the previous marker in the same sentence - or from the sentence start - up to itself. The marker sits on exactly the text its source supports. When the fragments of one sentence rest on different sources, each fragment carries its own marker. When one sentence rests on several sources jointly, one marker cites them all. A paragraph derived from a single source repeats one shared citation on every sentence - in AsciiDoc, through xref:#footnote-reuse[] - and a sentence that lacks a citation therefore stays visibly bare.

[.bad-example]
.{bad-icon} Bad example
====
One footnote at the end of a paragraph covers all four of its sentences. The third sentence is the author's own transition, but nothing distinguishes it, so the source appears to back a claim it never made.
====

[.good-example]
.{good-icon} Good example
====
The delivery sentence lists three modules: the ingestion module rests on the request for proposal, the reporting module on the vendor's product sheet, and the export module on the pricing workbook. Each fragment carries its own marker, so every module's origin stays checkable.
====

[#quote-and-locator]
==== Quote and Locator

Every source cited by a claim carries a verbatim quote and a locator. The [[quote,quote]]_quote_ is the source's exact wording that the claim rests on. It binds the two directions of support: the quote must entail the claim, and the claim must not assert more than the quote and its context support. The [[locator,locator]]_locator_ is the most specific address the source's format offers. A fixed-layout source can use a stable section number or name, a page, or both. A section locator is desirable when it takes the reader closer to the quoted text than the page alone, and the page can accompany it when the combination makes retrieval faster. The most common forms are the following:

. a section name or number, a page, or both for a fixed layout - a PDF or a printed book,
. a section name or number for an editable document,
. a sheet and row for a workbook,
. a file and line for code,
. a sender and timestamp for a message in a thread,
. a timestamp for a recording,
. a described region for an image.

The quote is omitted only where no wording exists to quote - a visual fact cited from an image. The locator then carries the reference alone. When a claim cites several sources, each source keeps its own quote and locator.

[.bad-example]
.{bad-icon} Bad example
====
The footnote names the storage specification and nothing else. To check one claim, the reader must re-read a 214-page document. Verification that costs that much doesn't happen.
====

[.good-example]
.{good-icon} Good example
====
The footnote cites the storage specification, page 12, and quotes: records are retained for 90 calendar days. The reader opens one page and compares one sentence against one claim.
====

[#attribution-in-citation]
==== Attribution Lives in the Citation

A cited claim carries its attribution in the citation itself, so the prose states the fact and doesn't also name the source. Phrases such as _the specification says_, _the report lists_, or _the contract requires_ repeat what the citation already records, and they make the reader pass through the source's identity before reaching the claim. A source is named in the prose only when its identity is the point. The cases are a fact new or changed relative to another source, a reconciliation of two sources that disagree, a claim marked as one source's opinion rather than settled fact, or a xref:#cross-references[cross-reference] to a fuller treatment.

[.bad-example]
.{bad-icon} Bad example
====
The specification says the retention period is 90 days, and the vendor's report lists three supported formats. (Both clauses narrate their source. The citations already attribute the claims, so naming the sources is redundant and delays each fact.)
====

[.good-example]
.{good-icon} Good example
====
The retention period is 90 days. Three formats are supported. (Each sentence states its fact and lets its citation carry the source. Naming a source in the prose is reserved for where its identity is the point, such as flagging that the 90-day period is new in version 3 of the specification.)
====

Every figure also carries a textual equivalent: alt text for short captions, or accompanying prose for figures that carry information not reproducible in alt text. A reader using a screen reader or reading a print copy without the figure should be able to extract the same information from the text alone.

[.bad-example]
.{bad-icon} Bad example

`image::architecture.png[]` (No caption. No alt text. A reader without the image gets nothing.)

[[part-2]]
== Technical Texts

This part adds rules for documents whose subject is a technical system: specifications, reference documentation, architecture documents, design documents, protocol descriptions, runbooks, and operator manuals. The rules in xref:#part-1[Part 1] still apply, and the following rules specialize them for technical writing.

=== Show, Then Tell - Technical Form

For technical content, the illustration called for by xref:#show-then-tell[Show, Then Tell] is a concrete artifact: a code snippet, a request/response pair, a configuration file, a query, or a diagram. When the behavior has interesting boundaries - empty inputs, missing inputs, concurrent access, partial failures, error conditions - illustrate at least one boundary alongside the typical case. Bugs tend to arise at boundaries.

[.bad-example]
.{bad-icon} Bad example
====
[source,python]
----
result = foo.do_thing(bar, baz)
print(result.stuff)
----
====

[.good-example]
.{good-icon} Good example
====
[source,python]
----
order = order_service.find_by_number("ORD-2026-00471")
order_service.cancel(order, reason="customer_request")
print(order.status)  # "CANCELLED"
----
====

=== Show the Wire

For network behavior, the illustration required by xref:#show-then-tell[Show, Then Tell] is the actual bytes - HTTP requests and responses, JSON payloads, SQL statements, or protocol frames - not a prose summary. The reader can then copy-paste and verify. Prose descriptions of network behavior tend to omit headers, status codes, content types, or escaping rules that turn out to matter.

[.bad-example]
.{bad-icon} Bad example
====
The client sends a POST request with the order data and receives the created order back.
====

[.good-example]
.{good-icon} Good example
====
[source,http]
----
POST /api/orders HTTP/1.1
Host: shop.example.com
Content-Type: application/json
Authorization: Bearer eyJhbGciOi...

{"customer_id": "C-4711", "items": [{"sku": "SKU-001", "quantity": 2}]}
----

[source,http]
----
HTTP/1.1 201 Created
Location: /api/orders/ORD-2026-00471
Content-Type: application/json

{"order_number": "ORD-2026-00471", "status": "PENDING_PAYMENT", "total": "59.80"}
----
====

[[diagrams-and-prose]]
=== Diagrams for Structure, Prose for Behavior

Use a diagram for static structure: components, layers, topology, state transitions, and data shapes. Use prose or code for dynamic behavior: what happens, in what order, under what conditions. A diagram doesn't convey behavior that prose expresses more precisely. Prose doesn't describe a tree or graph that a diagram conveys at a glance.

[.bad-example]
.{bad-icon} Bad example
====
A six-page sequence diagram with thirty messages, each labeled with a one-line description, and no accompanying prose.
====

[.good-example]
.{good-icon} Good example
====
A component diagram showing the client, gateway, order service, and payment service as boxes with the protocols between them, accompanied by prose that describes the request flow, the failure modes, and the retry rules.
====

=== ASCII Diagrams

When the rule xref:#diagrams-and-prose[] calls for a diagram, render it as an inline ASCII diagram if the structure fits. An ASCII diagram travels with the text - it survives copy-paste, renders in plain-text contexts, and doesn't depend on an asset pipeline. Use one when the topology genuinely earns a picture: a fan-out, a layered stack, a tree, a state machine with a small number of states. Skip it when one or two sentences of prose convey the same relationship, or when the structure is too large or too irregular to render legibly in characters.

A clean ASCII diagram has aligned components, consistent connectors, and labels that name each component. Boxes are drawn with one consistent set of characters throughout the document. Each arrow points in one direction and connects two named components. A diagram that forces the reader to count spaces or trace ambiguous connections is worse than the prose it replaced. Verbatim content, whether a diagram or a code listing, starts at the first column: the block supplies its own left inset, and a shared indent baked into the content doubles it.

[.bad-example]
.{bad-icon} Bad example
====
The gateway dispatches each incoming request to one of three downstream services - the search service, the catalog service, or the cart service - based on the request path. The search service queries an inverted index. The catalog service queries a relational database. The cart service queries a key-value store.

(The topology is a fan-out, and the reader has to assemble it from sequential prose. A diagram would show it at a glance.)
====

[.good-example]
.{good-icon} Good example
====
....
                +-----------+
                |  gateway  |
                +-----+-----+
                      |
      +---------------+---------------+
      |               |               |
      v               v               v
+-----------+   +-----------+   +-----------+
|  search   |   |  catalog  |   |   cart    |
+-----+-----+   +-----+-----+   +-----+-----+
      |               |               |
      v               v               v
+-----------+   +-----------+   +-----------+
|   index   |   |    db     |   |   redis   |
+-----------+   +-----------+   +-----------+
....

Each arrow is a synchronous call. The gateway routes by request path. Downstream services don't call each other.
====

=== Self-Contained Snippets

A code snippet compiles, parses, or runs as shown. Imports, package declarations, and necessary boilerplate are either included or explicitly elided with a comment such as `// imports omitted`. Snippets that combine several concerns into a fragment that doesn't run are a hidden cost: readers spend time reconstructing the missing parts.

[.bad-example]
.{bad-icon} Bad example
====
[source,python]
----
client.send(payload)
----
====

[.good-example]
.{good-icon} Good example
====
[source,python]
----
# imports omitted
client = Client(endpoint="https://api.example.com", timeout=5.0)
payload = {"event": "user.signed_up", "user_id": "U-12345"}
response = client.send(payload)
assert response.status_code == 202
----
====

[#code-markup]
=== Code Markup

Code, identifiers, file paths, configuration keys, and protocol headers are set in a monospaced font. Inline code uses backticks: `commit`, `org.example.api`, `/etc/app.conf`, `Content-Type`. Code blocks are tagged with a language for syntax highlighting. Identifiers are written exactly as they appear in code, including case.

[.bad-example]
.{bad-icon} Bad example
====
Call commit to persist the changes.
====

[.good-example]
.{good-icon} Good example
====
Call `commit` to persist the changes.
====

[[part-3]]
== AI Authorship

This part adds rules that apply when an AI system is given this guideline as a style instruction. The rules in xref:#part-1[Part 1] and xref:#part-2[Part 2] still apply. The following rules address failure modes specific to AI authorship: inventing facts, restating the prompt, opening with throat-clearing, narrating rule application, hedging from uncertainty, over-weighting items mentioned in the prompt, and treating the guideline's markup as content.

[#dont-invent-facts]
=== Don't Invent Facts

When you don't have a fact - an identifier, a path, a version number, a quotation, a citation, a metric, a date - state that you don't have it. Don't fabricate plausible-looking values. A reader uses the fact, and a fabricated fact becomes a defect that compounds with every downstream use.

ifdef::backend-html5+not-env-github[]
++++
<!-- vale English.Acronyms = NO -->
++++
endif::[]
[.bad-example]
.{bad-icon} Bad example
====
The service runs on Postgres 16.4 with `max_connections=300` and exposes a `/health` endpoint that returns the build SHA. (None of the version, parameter, or endpoint was stated in the input.)
====
ifdef::backend-html5+not-env-github[]
++++
<!-- vale English.Acronyms = YES -->
++++
endif::[]

[.good-example]
.{good-icon} Good example
====
The service runs on Postgres. The exact version and connection-pool configuration aren't stated in the input. Whether a health endpoint exists isn't documented either, and the service's route table would have to be checked to confirm.
====

[#dont-echo]
=== Don't Echo the Prompt

Begin with content. Don't open with a restatement of the request: "You asked about X. Here is information about X." The reader wrote the prompt. They don't need it read back to them.

Restating the audience and assumed knowledge to calibrate the document isn't echoing - see xref:#identify-audience[]. The prohibited pattern is summarizing the question back to the questioner before answering it.

[.bad-example]
.{bad-icon} Bad example
====
You asked about connection pooling. Here is a description of connection pooling. Connection pooling is a technique used in software systems to manage database connections.
====

[.good-example]
.{good-icon} Good example
====
A connection pool is a fixed-size set of pre-established connections that clients borrow for the duration of an operation and return when finished.
====

=== Don't Throat-Clear

++++
<!-- vale English.Quotes = NO -->
<!-- vale English.Preamble = NO -->
++++
endif::[]

This rule specializes xref:#no-throat-clearing[] for the AI failure mode. Don't open a response with service-style preambles - "Sure!", "Great question!", "I'd be happy to help.", "Of course!", "Certainly.", "Absolutely.", etc. The first sentence carries content.

++++
<!-- vale English.Quotes = YES -->
<!-- vale English.Preamble = YES -->
++++
endif::[]

ifdef::backend-html5+not-env-github[]
++++
<!-- vale English.Exclamation = NO -->
<!-- vale English.FirstPerson = NO -->
<!-- vale English.Preamble = NO -->
++++
endif::[]
[.bad-example]
.{bad-icon} Bad example
====
Sure! I'd be happy to explain HTTP connection pooling. Let me walk you through it step by step.

HTTP connection pooling is...
====

++++
<!-- vale English.Exclamation = YES -->
<!-- vale English.FirstPerson = YES -->
<!-- vale English.Preamble = YES -->
++++
endif::[]

[.good-example]
.{good-icon} Good example
====
An HTTP connection pool keeps a fixed number of TCP connections to a remote host open across requests. The client borrows a connection for one request, returns it on completion, and the pool reuses it for the next request to the same host.

=== Don't Annotate Rule Application

Don't tell the reader which rule from this guideline you are applying. "Per §3.2, I'll use direct verbs here" is meta-commentary, not content. Apply the rule. Don't narrate the application.

[.bad-example]

=== State Gaps, Don't Hedge

The xref:#no-hedging[] rule forbids softening claims with _usually_, _generally_, _somewhat_. When an AI author lacks a fact, the natural failure is to hedge: emit a softened claim that sounds plausible but conveys nothing the reader can act on. The right response is to name what's missing, not to weaken the assertion.

[#independent-verification]
=== Independent Verification

. Verification is strongest when the reviewer didn't write the text. An author who verifies their own citations reads each claim already believing it, and that belief survives a sympathetic re-reading, so a real defect slips past. A reviewer who never saw the draft, or a check that receives only the claim, the quote, and the source, holds no such belief and catches what the author overlooks. An independent reviewer, whether a second person or an AI subagent, runs the verification where one is available. Otherwise the author runs it, because a self-check, though weaker, beats none.
. A program such as a linter can check the citations, but its check isn't verification. It reaches only mechanical facts - whether a marker is well-formed, whether a xref:#quote[] appears in its source, and the like. Whether the quote entails the claim is a judgment, and no program makes it. A passing check therefore settles nothing about support, so the procedure of xref:#verify-citations[] still runs in full. The defect a check misses is the claim that asserts more than its quote carries - a count, an aggregate, or a second fact.

[#verify-citations]
=== Verify Every Citation

. Verification runs after the text is written and before delivery. Each xref:#citation-scope[citation] receives exactly one of the three verdicts defined below, and a repaired claim or citation re-enters verification. The pass ends when every citation holds _supported_ and every statement without a citation stands as xref:#author-supplied-claim[author-supplied] after the sweep below.
. Verify each citation against its xref:#source[], never against a memory of the source. Judge the quote before the claim: reading the claim first and asking whether the source agrees biases the judgment toward agreement. For every cited source, the check runs three steps in order.
.. Open the source at the xref:#locator[].
.. Find the xref:#quote[] verbatim at that place.
.. Re-read the claim and judge the support: the quote must entail the claim, and the claim must not assert more than the quote and its context support.
. Assign the verdict and act on it at once:
.. _Supported_ - the quote entails the claim and the claim stays within what the quote and its context support. No action follows.
.. [[unsupported-verdict,the unsupported verdict]]_Unsupported_ - the quote is present but doesn't entail the claim: the claim asserts more than the quote and its context support, or reports something different. Narrow or correct the claim until the quote entails it, or point the citation at a source that entails it. When no source entails the claim, xref:#dont-invent-facts[] governs it: state the gap or delete the claim.
.. _Not found_ - the quote or the locator doesn't exist in the source. Search the source for the intended support. When the source holds it elsewhere, repair the quote and the locator. When it doesn't, treat the citation as _unsupported_ with no entailing source.
. An xref:#inferred-claim[inferred claim] takes one more step. Verify every cited premise with the steps above, then judge whether the conclusion follows from the premises taken together. A conclusion that doesn't follow is _unsupported_ by its premises: narrow the conclusion until it follows, or delete it.
. After every citation holds _supported_, classify each statement that carries no citation by xref:#origin-test[]. A statement that derives from a source gets its citation and enters verification. Whatever remains stands as xref:#author-supplied-claim[author-supplied].
. Knowledge from training is the author's expertise. It yields xref:#author-supplied-claim[author-supplied claims], never citations, and a xref:#closed-source-list[source list] assembled from memory to look rigorous is fabrication. When the request requires sourced statements, consult sources and cite what was consulted.
. Never fabricate a xref:#quote[], a xref:#locator[], a xref:#source-identity[digest], or an entry of the xref:#closed-source-list[source list]. A fabricated citation is worse than a missing one, because it lends a claim the authority of a source that doesn't back it. The prohibition extends xref:#dont-invent-facts[] from values to support.
. A source that can't be opened again - deleted, expired, out of reach - makes its citations unverifiable. Mark each affected citation as unverifiable, tell the requester, and weaken or delete the claim that the requester can't confirm. Don't paraphrase the remembered source instead.
. A citation of the xref:#request-source[request] is verified against the request's text as it stands in the conversation.

[.bad-example]
.{bad-icon} Bad example
====
The draft cites page 41 for the retention period. The author remembers the specification well, finds the claim plausible, and ships. Page 41 covers backup schedules. Retention sits on page 12 and reads 30 days, not 90.
====

[.good-example]
.{good-icon} Good example
====
The author reopens the specification at the cited page and reads the quoted sentence before re-reading the claim. The claim says 90 days. The quote says 90 calendar days for standard tenants. The verdict is unsupported, and the claim is narrowed to standard tenants.
====

== AsciiDoc Documents

This part adds rules for the AsciiDoc markup that carries the document. The rules in xref:#part-1[Part 1], xref:#part-2[Part 2], and xref:#part-3[Part 3] still apply. They govern the prose. This part governs the markup the prose is written in.

[#one-sentence-per-line]
=== Don't Write One Sentence Per Line

Write each paragraph as continuous prose. Don't start a new source line for every sentence. AsciiDoc joins consecutive non-blank lines into one paragraph, so a per-sentence line break produces no change in the rendered output. The source reads as a list of fragments instead of a paragraph. A sentence edit no longer aligns with the unit a reader thinks in.

[.bad-example]
.{bad-icon} Bad example
====
[source,asciidoc]
----
The cache stores recently used entries.
Each entry has a key and a value.
An entry is evicted when the cache is full.
----
====

[.good-example]
.{good-icon} Good example
====
[source,asciidoc]
----
The cache stores recently used entries. Each entry has a key and a value. An entry is evicted when the cache is full.
----
====

[#numbered-paragraphs]
=== Numbered Paragraphs

A _numbered paragraph_ is a paragraph written as an item of an AsciiDoc list, so that the renderer prefixes it with a number, a letter, or - at the deepest levels - a bullet. Numbering makes each paragraph an addressable unit: a review comment or a cross-reference names item 2.3 instead of "the second sentence of the fourth paragraph." A numbered paragraph is still a paragraph - full sentences developing one topic, as xref:#one-paragraph-one-topic[] requires. Numbering addresses paragraphs. It doesn't license the fragment-style bullets that xref:#lists-for-enumerable-content[] forbids.

[#number-every-paragraph]
==== Number Every Paragraph of a Multi-Paragraph Section

When the body of a section contains two or more paragraphs, every paragraph of that body is a xref:#numbered-paragraphs[numbered paragraph]. A section whose body is a single paragraph is written as plain prose. The numbering enforces xref:#one-paragraph-one-topic[] at the markup level: each number marks the start of one topic, so a paragraph that drifts into a second topic is exposed - the second topic sits under a number that promised the first.

[.bad-example]
.{bad-icon} Bad example
====
[source,asciidoc]
----
== Eviction

A cache entry is evicted when its TTL expires. Eviction runs synchronously on each insertion.

The eviction order is least-recently-used. The order is tracked per shard.

Evicted entries are counted in the `cache_evictions_total` metric.
----

(Three paragraphs, none addressable. A reviewer pointing at the second one has to describe its position.)
====

[.good-example]
.{good-icon} Good example
====
[source,asciidoc]
----
== Eviction

. A cache entry is evicted when its TTL expires. Eviction runs synchronously on each insertion.
. The eviction order is least-recently-used. The order is tracked per shard.
. Evicted entries are counted in the `cache_evictions_total` metric.
----
====

[.good-example]
.{good-icon} Good example
====
[source,asciidoc]
----
== Eviction

A cache entry is evicted when its TTL expires. The eviction order is least-recently-used.
----

(A single-paragraph body stays plain prose. A lone number would have nothing to be ordered against.)
====

[#numbering-depth]
==== Numbering Depth

xref:#numbered-paragraphs[Numbered paragraphs] nest at most six levels. The first four levels are ordered-list markers written with dots - `.`, `..`, `++...++`, `++....++`. The fifth and sixth levels are unordered-list markers - `++*++`, `++**++`. The renderer shows the fifth and sixth levels as bullets instead of numbers, and the other rules of this section apply to them all the same. Nothing nests below `++**++`:

[source,asciidoc]
----
. 1
.. 2
... 3
.... 4
* 5
** 6
----

Material that seems to need a seventh level doesn't get one. The subtree is restructured instead: the top of the subtree is promoted to a subsection heading per xref:#section-nesting[], or intermediate levels that don't carry real hierarchy are flattened.

[.bad-example]
.{bad-icon} Bad example
====
[source,asciidoc]
----
.... The client retries a failed request.
..... The retry delay doubles on each attempt.
*** The delay is capped at 30 seconds.
----

(Five dots exceed the four-dot ladder, and `++***++` exceeds the two-asterisk ladder. After `++....++` come `++*++` and `++**++`, and nothing comes after `++**++`.)
====

[.good-example]
.{good-icon} Good example
====
[source,asciidoc]
----
.... The client retries a failed request.
* The retry delay doubles on each attempt.
* The delay is capped at 30 seconds.
----
====

[#no-lone-numbered-paragraph]
==== No Lone Numbered Paragraph

At every nesting level, a xref:#numbered-paragraphs[numbered paragraph] has at least one sibling at the same level under the same parent. A level holds zero items or two or more. A lone item means the numbering does no work: there is nothing at that level to order the item against, so its content belongs in the parent paragraph's own text or in a continuation per xref:#continuation-content[] - or a sibling is missing. The rule mirrors xref:#section-nesting[], which forbids a lone subsection for the same reason.

[.bad-example]
.{bad-icon} Bad example
====
[source,asciidoc]
----
. The pool validates a connection before lending it.
.. The validation query is `SELECT 1`.
. The pool replaces a connection that fails validation.
----

(The `..` item has no sibling. It elaborates its parent rather than enumerating anything.)
====

[.good-example]
.{good-icon} Good example
====
[source,asciidoc]
----
. The pool validates a connection before lending it. The validation query is `SELECT 1`.
. The pool replaces a connection that fails validation.
----

(The lone item is folded into its parent.)
====

[.good-example]
.{good-icon} Good example
====
[source,asciidoc]
----
. The pool validates a connection before lending it.
.. The validation query is `SELECT 1`.
.. A validation that exceeds 250 ms counts as a failure.
. The pool replaces a connection that fails validation.
----

(The missing sibling is supplied, so the nested level now enumerates two facts about validation.)

[#paragraph-headers]
==== Paragraph Headers

A xref:#numbered-paragraphs[numbered paragraph] may open with a _paragraph header_ - a bold phrase that names the paragraph's topic. The header stands alone on the item's line. The paragraph's text follows as a continuation per xref:#continuation-content[] or as nested numbered paragraphs. A paragraph header uses sentence case: the first word and any proper nouns, acronyms, or identifiers are capitalized, while ordinary words that follow remain lowercase. It never uses title case and never ends with a period. A header is due when it helps the reader scan: the paragraph is long and holds several sentences, or the item heads a group of nested items whose shared topic needs a name. A header is omitted when it adds nothing: a paragraph of one or two sentences whose topic is already stated by the section heading doesn't restate that topic in bold. A paragraph header is the one place where bold appears in body text - see xref:#inline-formatting-semantics[].

[#explicit-anchors]
=== Explicit Anchors

A part of the text that a cross-reference targets carries an explicit anchor: a block anchor `+[[kebab-case-id]]+` on the line directly above a heading, or an inline anchor of the same form placed directly on text inside a block. The anchor sits on the narrowest span that alone defines the referenced concept. To choose that span, apply the following tests from narrowest to broadest and stop at the first that holds:

. A single word defines the concept. Anchor that word.
. One sentence or one list item defines it. Anchor that sentence or item.
. One paragraph defines it. Anchor that paragraph.
. Only the section as a whole defines it. Anchor the section with a block anchor on the line above its heading.

An anchor ID is a lowercase kebab-case name in the document's language, and it names the content, not the content's position. An explicit ID survives retitling. An auto-generated ID is derived from the heading text, so renaming the heading silently breaks every reference to it.

[.bad-example]
.{bad-icon} Bad example
====
[source,asciidoc]
----
== Configuration

The defaults are listed in <<_connection_pool>>.

=== Connection Pool
----

(The reference targets the auto-generated ID. Renaming the heading to "Pooling" breaks the reference.)
====

[.good-example]
.{good-icon} Good example
====
[source,asciidoc]
----
== Configuration

The defaults are listed in the section xref:#connection-pool[].

[[connection-pool]]
=== Connection Pool

A [[lease]]_lease_ is the exclusive right to use one pooled connection for the duration of an operation. [[pool-size-default]]The default pool size is 10.
----

(The section keeps its ID under any title. The anchors sit on the most specific defining parts: the section for the pool, the word for the lease, the statement for the default size.)
====

[#internal-references-with-xref]
=== Internal References with `xref`

In each paragraph that uses a concept defined elsewhere in the document, at least the first use links to the definition. Later uses in the same paragraph may stay plain. The link is written with the `xref` macro against the definition's explicit anchor. The default form is `+xref:#connection-pool[]+` with empty brackets, which renders the target's title and stays correct when the title changes. Custom link text is supplied only when the title doesn't fit the grammar of the sentence. When a reference points to a section and the rendered title alone would leave the grammar or the meaning of the sentence unclear, the reference is preceded by a qualifier such as _the section_ or _the chapter_. xref:#cross-references[] governs the wording around the reference. This rule governs when a reference is due and the markup that carries it.

[[no-section-heading-self-references,no section-heading self-references]]A cross-reference never targets the heading of the current section, defined as the section begun by the nearest preceding heading. The reader is already inside that section, so the link provides no navigation and falsely suggests another destination. Write the current section's name as plain text. The prohibition applies only to the current section's heading. A concept or another anchor defined within the same section remains subject to the paragraph-level linking rule: in each paragraph that uses it, at least the first use links to the precise definition.

[.bad-example]
.{bad-icon} Bad example
====
[source,asciidoc]
----
Each handler holds a lease on a pooled connection. Pool sizing is described in the section "Connection Pool" above. Defaults are listed in xref:#connection-pool[].
----

(The term _lease_ is defined elsewhere in the document but isn't linked to its definition. The first section reference is plain text: it doesn't link, and it breaks when the section moves or is retitled. The last reference links, but it renders as "listed in Connection Pool" - without a qualifier the meaning of the sentence is unclear.)
====

[.good-example]
.{good-icon} Good example
====
[source,asciidoc]
----
Each handler holds a xref:#lease[lease] on a pooled connection. Pool sizing is described in the section xref:#connection-pool[]. Size the pool according to the xref:#connection-pool[sizing rules].
----

(The defined term links to its definition. The empty-bracket form inherits the target's title, and the qualifier _the section_ keeps the meaning of the sentence clear. The last reference supplies custom text because the sentence needs a different inflection.)
====

[[anchor-reference-text,an anchor that declares a reference text]]The empty-bracket form takes its text from the target's reference text. A section supplies its title. Any other anchor - on a paragraph, a list item, or a word - supplies a reference text only when the anchor declares one, in the form `+[[anchor-id,reference text]]+`. An empty-bracket reference against an anchor without a reference text renders the raw anchor ID, which is a defect. When the target isn't a section, either declare the reference text on the anchor or supply custom link text in the reference.

[.bad-example]
.{bad-icon} Bad example
====
[source,asciidoc]
----
[[retention-schedule]]The retention schedule keeps records for 90 days.

The purge job applies xref:#retention-schedule[].
----

(The anchor sits on a paragraph and declares no reference text, so the reference renders as the raw ID: "The purge job applies [retention-schedule].")
====

[.good-example]
.{good-icon} Good example
====
[source,asciidoc]
----
[[retention-schedule,the retention schedule]]The retention schedule keeps records for 90 days.

The purge job applies xref:#retention-schedule[].
----

(The anchor declares a reference text, so the reference renders as "The purge job applies the retention schedule.")
====

[#bibliography-markup]
=== Bibliography

The closed source list of xref:#closed-source-list[] is written as a bibliography: the last section of the document, titled _Sources_, with the block anchor `+[[sources]]+` on the line above its heading. Each source is one ordered-list item that opens with an anchor of the form `+[[id,Reference Label]]+` - xref:#anchor-reference-text[]. The anchor id is lowercase kebab-case, per xref:#explicit-anchors[]. The native https://docs.asciidoctor.org/asciidoc/latest/sections/bibliography/[AsciiDoc bibliography attribute^], `[bibliography]`, isn't used, because its rendering bypasses the reference labels.

The _reference label_ is the short name that every reference to the entry renders, so a reference needs no custom link text. A label reads meaningfully on its own - an author and a year, a short title, a standard's number - and is unique among the entries and different from the id. The item line carries the label alone, in italics.

The entry's fields follow the item line, one per line, each written as a `Key::` marker and its value, opened by the attribute line `[horizontal.source-fields]` that renders the record small and two-columned. The keys and their order come from the dimensions of xref:#source-identity[]: `Title` first, then `Type` and the type's fields per xref:#source-types[], then the xref:#source-status[status] field, then the class fields. `Title` is omitted when the label already gives the title. Literal values - the archive path, the digest - stay monospaced.

[#citation-footnotes]
=== Citation Footnotes

A _citation footnote_ is a footnote whose body opens with a reference to an entry of the xref:#bibliography-markup[bibliography] and attaches a claim to its sources. One item carries one source: the reference, then after a comma the xref:#locator[], then after a colon the xref:#quote[]. Several items are separated with a semicolon and a space:

[source,asciidoc]
----
The retention period is 90 days.footnote:retention[<<storage-spec>>, p. 12: "+records are retained for 90 calendar days+".]

The rule covers every tenant.footnote:retention[]

Two phases lower the delivery risk.footnote:phasing[Inferred from: <<storage-spec>>, p. 4: "+phase one comprises modules A and B+"; <<brief>>: "+we cannot absorb a big-bang rollout+".]
----

[[footnote-reuse,the footnote reuse]]The empty-bracket form re-cites an earlier footnote under the same number, so a paragraph derived from one source repeats its citation per sentence without repeating the text. The prefix `Inferred from:` marks the claim classes of xref:#claim-classes[]: with it the footnote cites the premises of an xref:#inferred-claim[inference], without it the footnote backs a xref:#reported-claim[reported claim].

The xref:#quote[] is written between paired delimiters: a quotation mark, a plus sign, the quoted wording, a plus sign, a quotation mark. Each mark carries a duty. Quotation marks show the source's wording as a quotation in the body font. Plus signs keep the bytes exact - no substitution rewrites dashes or symbols - and the quote can therefore be searched in the xref:#archived-file[archived source] byte for byte. Evidence, not the author's prose, stands between them, so the rules that govern the author's language don't reach the quote. A `]` inside the quote is escaped as `\]`, which otherwise would end the footnote.

A footnote whose body doesn't open with a reference to the xref:#bibliography-markup[bibliography] is an ordinary footnote, and no rule of this section restricts it.

An external link doesn't replace a citation. A statement that rests on a web source cites the source's bibliography entry, and the address lives in that entry's `URL` field.

[.bad-example]
.{bad-icon} Bad example
====
[source,asciidoc]
----
The retention period is 90 days.footnote:[see the specification]
----

(The footnote gestures at a source without citing one: no bibliography reference, no locator, no quote. The claim stays unattributed and unverifiable.)
====

[#footnote-punctuation]
=== Footnote Punctuation

The text of a footnote ends with a period. The rule covers every footnote alike: an ordinary footnote closes its sentence, and a xref:#citation-footnotes[citation footnote] closes with a period after its last source item. A footnote without terminal punctuation reads as truncated, and mixed footnote punctuation across one document reads as noise. A reuse of the form `+footnote:id[]+` carries no text of its own, so nothing is there to close.

[.bad-example]
.{bad-icon} Bad example
====
[source,asciidoc]
----
The limit is 5 GB.footnote:[Set by the storage tier]
----
====

[.good-example]
.{good-icon} Good example
====
[source,asciidoc]
----
The limit is 5 GB.footnote:[Set by the storage tier.]

The retention period is 90 days.footnote:retention[<<storage-spec>>, p. 12: "+records are retained for 90 calendar days+".]
----
====

[#link-text-carries-the-claim]
=== Link Text Carries the Claim

An external link wraps the phrase that the linked source substantiates, so the sentence keeps its meaning when the markup is stripped. Link text such as _here_ or _this page_, and a bare URL pasted mid-sentence, carries no information about the target. A link that leads the reader away from the document ends with `^`, which opens the target in a new tab.

[.bad-example]
.{bad-icon} Bad example
====
[source,asciidoc]
----
The upload limit is documented here: https://docs.example.com/assets/limits.
----
====

[.good-example]
.{good-icon} Good example
====
[source,asciidoc]
----
The service https://docs.example.com/assets/limits[accepts uploads of up to 5 GB per file^].
----

(The linked phrase is the claim the source substantiates. The sentence keeps its meaning without the markup.)
====

[#inline-formatting-semantics]
=== Inline Formatting Semantics

Each inline mark has one role. A monospaced span marks technical literals - paths, domains, IP addresses, file extensions, configuration keys, HTTP headers, identifiers - as xref:#code-markup[] prescribes. Italics mark a term of art, a foreign-language term, the proper name of a product or interface element, a word mentioned as a word, and a word that carries emphasis. Bold appears in headings, where the renderer applies it, and in the paragraph headers prescribed by xref:#paragraph-headers[]. Elsewhere, bold isn't written in body text - a word that needs emphasis in a paragraph is italicized.

[.bad-example]
.{bad-icon} Bad example
====
[source,asciidoc]
----
The *connection string* is stored in _config.yaml_ under the key *db.url*.
----

(Bold in body text - twice - and italics for a path. Emphasis belongs to italics, and paths belong to monospaced spans.)
====

[.good-example]
.{good-icon} Good example
====
[source,asciidoc]
----
A _connection string_ is a URL-shaped value that names the database host, port, and schema. The connection string is stored in `config.yaml` under the key `db.url`. The value follows the _JDBC_ URL convention.
----
